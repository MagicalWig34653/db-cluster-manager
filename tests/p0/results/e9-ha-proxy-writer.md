## Part B: coordinated writer choice (ADR 0017)

Layout: proxy-a on m2 and proxy-b on m3 (containers on the cluster overlay, `coordination` against a socat TLS front on `:8443` of every VM, which is lab plumbing because the proxy requires HTTPS to non-loopback managers), keepalived VIP, four clients on m1 writing every 50 ms (VIP/failover list, per-connection/persistent, 1 s timeout). Rows carry the commit time of the serving node.

| Scenario | Observed |
| --- | --- |
| Agreement | Both proxies reported the same writer at every aligned sample (initial writer n1, epoch 1). In E8 independent proxies picked n2 and n3. Direct writes through both proxies in a 20 s test all landed on one node (the script's assertion reported "more than one node" only because the label of an earlier run, n1, was reused: log stage 5 vs 6; the new run's rows are n2 only). |
| Controlled switch n2 -> n1 -> n3 -> n2 (under load, 4 clients x 20 writes/s) | Each switch: both proxies report `has_writer false, pending <target>` for **1.0 s** (10 samples), then the new writer with the next epoch. Rows: n2 until 06:45:04.050, n1 from 06:45:05.119, n3 from 06:45:22.159 ... no interleaving of two writers in commit order (3 hand-overs, 3 writers, 0 interleavings). Clients: one error burst per switch (`no usable writer`), longest gap without success **1.1 s**. The two proxies' status samples differ for at most 1 sample (100 ms) around each transition, never with two different non-empty writers (the "9 different" samples compare `none` with a writer, i.e. one proxy has already frozen). |
| Proxy unreachable (a): proxy-b cut off from the manager front while a switch to n1 was requested | Switch became pending at once: proxy-a `no writer, pending n1` for **26.1 s** (writes unavailable, `no usable writer`), proxy-b kept serving n2 for 25.6 s (it could not see the freeze). After the partition healed proxy-b froze and both completed: switch complete 26 s after the request, hand-over gap in commit order 505 ms. **No sample with two different writers.** This is the intended "switch blocked, writes stop" behaviour; the cost is the outage of the whole write path while one proxy is unreachable. |
| Proxy unreachable (b): proxy-b container stopped | Switch pending for **28 s** until proxy-b was started again (proxy-a without writer the whole time, clients: 28.7 s without success); proxy-b came up with `unknown`, read the pending epoch, acknowledged, and the switch completed 0.7 s later. No second writer. |
| Manager unreachable (all three replicas scaled to 0, 28 s) | proxy-a kept writer n2 and epoch 7 throughout (1034 x 200/n2); clients saw 10-11 errors and a 4.3 s gap without success from 11:37:08; whether this gap is caused by the manager outage or by the restart of proxy-b (VIP clients reconnect) was not separated. | Proxy kill (VIP holder's container, no restart) | VIP clients 2.0 s without success (connection refused/timeout), failover-list clients 0.4 s (one error each). VIP moved to the peer; no split writer (single node n2). |
| Whole VM of proxy-a (writer node, manager replica) hard-stopped | proxy-b reported **no writer for 62 s** (writer node gone, it must not choose another itself), then a switch to n1 was requested while proxy-a was unreachable: stayed pending, as intended. When the VM was started (13 s) it completed: writes resumed **14 s after `limactl start`** (switch completed via the returned proxy-a), clients had up to 1m10s without success. Then proxy-b had no writer for another 11 s (epoch 9, second freeze while the node n2 recovered) before serving n2. |
| Integrity | No acknowledged write lost in any scenario; every client's `ok` count is at most the rows in the database (committed but unacknowledged rows: up to 12 per client in the partition scenarios). Distinct writer nodes per scenario: K1 n2, mgr n2, switch scenarios one node per interval, no interleaving. |

**What this does not show:** sample resolution is 100 ms, so a sub-100 ms overlap is not excluded; the VIP was never held by both VMs where sampled (`neither` periods during moves); autoFailover (`E9_AUTOFAILOVER=true`) was **not exercised** (manual switches only); the loss of the proxy VM left the cluster with no writer for 62 s because nothing switches the writer unless an operator (or autoFailover) does; the manager front is a lab socat; TLS verification of the proxy to the manager used a lab trust file.

## Part C: B2/B3 power loss, diagnosis of the stuck node

B1 (one VM power loss) first: cluster back to three Synced, node n3 rejoined by **IST** this time ("IST sender 38022 -> 38105", `State transfer ... complete`), same UUID, no bootstrap. B2 (all three VMs `limactl stop --force`): VMs and Swarm back 25-60 s after the first start, the manager stack restarted by Swarm (**three manager tasks running 20 s after the first VM was reachable**, a replica leading 1 s later; the lab-unit restart of E8 is not needed). In 150 s the manager did nothing (no spec change, no bootstrap, no operation), as in E8. Two nodes formed a Primary component from `gvwstate.dat` by themselves (size 2), n3 never joined within 600 s: its task failed with exit 1 every 22-23 s.

**Cause of the n3 failure (diagnosis from the kept VMs, container logs read per container; excerpts below were read manually and are not all in the log):**

- The Primary component of n1/n2 reports `wsrep_cluster_state_uuid = 00000000-0000-0000-0000-000000000000` (logged by `e8_status3`) and, in the joiner's log, `group UUID = 00000000-...` / `Group state: 00000000-0000-0000-0000-000000000000:88`: after the power loss all three nodes had `uuid 00000000-... seqno -1` in `grastate.dat`, and the component restored from `gvwstate.dat` did not recover the real group UUID.
- n3 starts, requests a state transfer, SST (mariabackup) streams, then `WSREP: Failed to parse uuid:seqno pair: ':86'` and `Receiving IST failed, node restart required: IST receiver reported failure: 'IST started with wrong seqno: 86, expected <= 0' (22)`, `Failed to JOIN the cluster after SST gcs_join(00000000-...:-1) failed`, `Aborting`, exit 1. The donor's SST position has no UUID; the joiner's `:86` cannot be parsed, so the join fails every time, Swarm restarts, same result. Disk space (15 GiB free), memory and OOM were excluded (`oom=false`).
- **Root cause (diagnosed, not fixed): a Primary component re-formed from `gvwstate.dat` after a total power loss has an unknown (zero) cluster UUID; a node that must take a state transfer from it cannot join.** This explains E8's unexplained n3 failure and its later "no Galera state" diagnosis answer in the sense that the whole cluster is in a state the product does not know. The surviving two-node component stays Primary and serves writes in the meantime (sentinel rows were present).
- The manager's `POST .../outage-diagnosis` after the operator scaled all three services to 0 answers **409 conflict** (`helper: no candidate`); the API gives no reason and the manager log had no line. It was not investigated further (likely `ErrNotFullOutage`/`ErrNoCandidate`; the cause is not established). A guided recovery after a VM power loss was therefore **not exercised**.
- After the services were scaled back to 1 the cluster did not come back within 600 s again (the same exit 1 loop). B3 (staggered loss) ran on this broken state: its result ("hands off", then no candidate) is **not a valid B3 result**; the stale-node question stays open.

No product change was made: there is no clear small bug with a test-first fix, the behavior belongs to MariaDB Galera recovery (11.4.13) and needs a decision (operator guidance: bootstrap from the node with the highest seqno; or the manager's diagnosis must understand the zero-UUID Primary component). Recommendation, not implemented: the health observation should flag "Primary component with zero group UUID" as an incident, and the outage diagnosis should explain its 409.

## Script defects found

- `docker service logs` hangs for good on a slot that keeps failing (also E8 run 2): E9 reads container logs per container (`e8_slot_logs` override); two hung processes of the script were killed by hand and the run continued.
- Stage 5 address bug (above); `node_vm` is empty when all slots are scaled to 0 (`refusing to address non-lab VM ''` lines in stage 11).
- B3 and the guided recovery were run on the stuck cluster by the script's order; they should be re-run after the cluster state is repaired.
