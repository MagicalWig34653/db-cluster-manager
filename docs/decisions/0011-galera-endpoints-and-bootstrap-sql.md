# ADR 0011: Galera monitoring endpoint, volume ownership, bootstrap accounts and job image

Date: 2026-10-22
Status: Proposed. Implemented in `internal/galera` (spec and plan steps), `internal/agent` (`init-volume-dirs`, `exec-sql`), `internal/dbadmin` (bootstrap templates), `internal/galeraprobe` (`Admin` executor), `internal/runner`, `internal/dbbackup` (restore plans), `cmd/agent`, `cmd/dbcm-job` and `deploy/Dockerfile.jobs`. Tested only with fakes: a fake MySQL server on a unix socket, temporary directories and an in-memory Docker. **Nothing here has run against real MariaDB, a real Swarm or a built image.** Reopen after lab E4.

## Context

The fourth batch left two gaps that block the Swarm trial (STATUS "Fourth batch"): the manager's health collector asks the agent to query `<volume root>/run/mysqld.sock` (`manager.DefaultMonitorSocket`), but the Galera spec kept MariaDB's socket in the container's `/run/mysqld`; and backups need a backup account, a monitoring account and an image with `mariabackup`, none of which existed. The volume is created by the agent as root, while `mariadbd` runs as the image's `mysql` user.

## Decision

1. **Monitoring endpoint: the unix socket on the node volume.** The spec passes `--socket=/dbcm/run/mysqld.sock` (`galera.SocketPath`; `socket` is a managed argument that TLS pass-through cannot override). On the host it is `<volume root>/run/mysqld.sock` = `agent.DefaultSocket` = `galera.SocketRelPath` = `manager.DefaultMonitorSocket` (a compatibility test keeps them equal). It is in its own directory, not in the datadir (SST empties the datadir, E1) and not at the volume root (see 2). The agent confines the resolved socket path below the volume base (`collect-health`) or below the verified volume root (`exec-sql`).
2. **Volume ownership: new agent command `init-volume-dirs` and plan step.** After `init-identity`, the agent verifies the marker and creates `data/` and `run/` with mode 0750, owned by the configured numeric database user (`galera.Cluster.DBUID/DBGID`, default 999:999). All access goes through an `os.Root` at the volume root; an existing entry must be a real directory (Lstat, never followed), and `fchown`/`fchmod` act on the opened directory after an `os.SameFile` check, so a swapped entry cannot redirect the change. The volume root and the marker are not touched: they stay root-owned, so the database user can neither replace nor remove the marker. Existing content is left alone (the image entrypoint, running as root, already chowns datadir files to `mysql`). The step is added to cluster creation, node replacement, cluster restore (the restore job now runs after it) and inspection restores.
3. **Bootstrap accounts: plan steps `exec-sql` with allow-listed templates.** When `galera.Cluster.Accounts` names the password secrets, `PlanCreate` adds, after the bootstrap node is Synced at size 1 and before the first joiner, `create-monitor-user` (default `'dbcm_monitor'@'localhost'`, USAGE only, ADR 0008) and `create-backup-user` (default `'dbcm_backup'@'%'`). Galera replicates account statements; joiners receive them by SST. Without a monitor secret the plan warns that health collection will fail. Templates (`internal/dbadmin/bootstrap.go`):
   - `create-monitor-user`: `CREATE USER IF NOT EXISTS`, `ALTER USER ... IDENTIFIED BY ... REQUIRE NONE|SSL`, `REVOKE ALL PRIVILEGES, GRANT OPTION` (idempotent; a pre-existing account loses extra privileges). No GRANT.
   - `create-backup-user`: the same, then `GRANT RELOAD, PROCESS, LOCK TABLES, BINLOG MONITOR ON *.*` — the list in the MariaDB documentation "mariadb-backup Overview", section Authentication and Privileges, for 10.5+ (verified 2026-10-22). Not granted: `CONNECTION ADMIN` (only for `--kill-long-queries-timeout`, unused), `REPLICA MONITOR`/`SLAVE MONITOR` (only for `--slave-info`; the job uses `--galera-info`), `SUPER` (only MyRocks). With `backup_logical` also `SELECT, SHOW VIEW, TRIGGER, EVENT, SHOW CREATE ROUTINE` for the per-database `mariadb-dump` export (`SHOW CREATE ROUTINE` exists since 11.3).
   - `set-root-password`: `ALTER USER 'root'@'localhost'|'root'@'%' IDENTIFIED BY ...` (rotation; nothing else).
   
   User and host pass the dbadmin allowlists, system accounts (`root`, `mysql`, `mariadb.sys`) are refused for the create templates, and the password must pass `dbadmin.ValidatePassword` (no quote, backslash or control character), so no input can end a literal. The agent re-renders the template at decode time with a placeholder password, so every template error is an invalid command; unknown fields (for example `sql` or `password`) are refused by strict JSON decoding. Results and the step record hold only the redacted statements (`IDENTIFIED BY '***'`); driver errors are redacted for both passwords.
4. **Credential flow (designed; manager side not implemented).** The manager generates each password with `dbadmin.GeneratePassword` and creates Swarm secrets labelled with the installation: the plain monitor password (the agent already mounts it through `AgentTransport.MonitorSecret` and passes it to `-monitor-password-file`), the plain backup password (agent mount, used by `exec-sql`), and an option file for jobs rendered with `dbadmin.RenderOptionFile` (`RunBackupArgs.DBCredentialSecret`). `exec-sql` connects through the node socket as `root` with the cluster's `RootPasswordSecret`; the agent reads every password from its own secret mount (`-db-secrets-dir`, default `/run/secrets`) through an `os.Root`, by secret name, never from command arguments. Consequence: **the agent service must mount the cluster's root password secret and the backup password secret.** Attaching them (a service update of the global agent service, which restarts the agents one by one) is not implemented; until it is, `exec-sql` returns `not-configured`.
5. **Job image `deploy/Dockerfile.jobs` and `cmd/dbcm-job`.** Final stage `mariadb:11.4.13@sha256:250e1609e93c0e6aecf64bfbab2d84d5e89d2481540fe77447ff6c855c3b1873` (multi-arch index digest from the Docker Hub registry API; it equals the digest E1 pulled as `mariadb:11.4`), plus the static helper built from the pinned Go image. `dbcm-job` wires `dbbackup.RunJob`: tools resolve only in `/usr/bin` and `/usr/local/bin` with a fixed environment (no shell, `$PATH` ignored, only `dbbackup.AllowedTools`), stdin is copied by the runner so a read error kills the tool, non-zero exit is an error. It runs as `USER 999:999` (the image's `mysql`), which owns `data/` after `init-volume-dirs`: a physical backup can read and a physical restore can write the datadir without root. `scripts/check_deploy.py` checks the pin, the final base, the entrypoint (`agent.JobCommand`), numeric non-root user equal to the galera default owner, the build-time tool check against `dbbackup.AllowedTools`, and no `EXPOSE`/`VOLUME`. No image was built (the host Docker daemon is not used).

## Evidence (what was verified, and how)

- **mysql UID/GID.** The official Dockerfile (`MariaDB/mariadb-docker`, `11.4/Dockerfile`, read with `gh api`) runs `groupadd -r mysql && useradd -r -g mysql mysql` without fixed IDs. The `/etc/passwd` and `/etc/group` of `mariadb:11.4.13` (linux/arm64 manifest `sha256:2839e4d3…`, second layer `sha256:5e6ac9c5…`, fetched from the registry with curl, no Docker daemon) contain `mysql:x:999:999` and `mysql:x:999:`. The amd64 image was not inspected. E1 chowned the datadir to 999:999 and worked.
- **Tools in the base image.** The 67 MB layer `sha256:d0215179…` of the same arm64 image lists `/usr/bin/mariadb-backup`, `/usr/bin/mariabackup -> mariadb-backup`, `/usr/bin/mbstream`, `/usr/bin/mariadb-dump` and `/usr/bin/mariadb`. Image config: `User` empty, `Entrypoint ["docker-entrypoint.sh"]`, version label 11.4.13.
- **Entrypoint behaviour** (`11.4/docker-entrypoint.sh`): `SOCKET` is read from the server configuration including command-line arguments; when running as root it chowns datadir files not owned by `mysql` and the socket's directory (`find "${SOCKET%/*}" -maxdepth 0 …`), which therefore must exist; root@localhost is created by `mariadb-install-db --auth-root-authentication-method=normal` with the password from `MARIADB_ROOT_PASSWORD_FILE` (no unix_socket authentication for root).
- **SST and the socket.** `wsrep_sst_mariabackup.sh` (MariaDB 11.4) passes the server's socket (`WSREP_SST_OPT_SOCKET`) to mariadb-backup, so moving the socket should not break SST.
- **Driver.** go-sql-driver/mysql 1.10.1 executes the statements over a unix socket against the fake server, one connection, no interpolation, no multi-statements.

## Alternatives

- **Host-published loopback-only port.** Swarm cannot express it: `mode: host` publishing binds all host addresses (`PublishedPort` has no host IP in the Swarm API), and ingress publishing exposes the port on every node through the routing mesh. A firewall rule would be needed on each host, outside the installation's ownership inventory. The socket needs no port, no network exposure and no TLS. Kept as a fallback for setups where the volume path cannot be shared (agent `collect-health` still accepts a loopback address).
- **Socket in the datadir.** Rejected: SST empties the datadir (E1), and the database user may write there.
- **`init-volume-dirs` folded into `create-volume`.** Rejected: `create-volume` runs before the identity exists; the ownership change should only happen on a volume whose marker the agent has verified. A separate step is also replayable on its own.
- **Recursive chown.** Rejected: unbounded work on a populated volume; the entrypoint already handles datadir files.
- **Image init scripts (`/docker-entrypoint-initdb.d`) as a Swarm config.** No root password in the agent, but runs only on first initialization, gives no result back to the manager and cannot rotate. Possible fallback if mounting the root secret into the agent is rejected.
- **unix_socket authentication instead of the root password.** Would avoid the root secret in the agent, but the image creates root@localhost with password authentication only, `mysql@localhost` (unix_socket) has only the SST grants, and go-sql-driver has no `unix_socket` client plugin.
- **Running the SQL as a one-shot job service** (like backups) that mounts the secrets. No agent restart for new secrets, but needs task-exit observation that the agent does not have yet. Candidate if attaching secrets to the agent service proves disruptive.
- **Job image from `ubuntu:noble` plus MariaDB packages.** Avoids the inherited `VOLUME /var/lib/mysql`, but duplicates the repository setup of the official image and risks a tool/server version skew.

## Unverified assumptions (lab E4 must confirm)

1. `mariadbd` starts with `--socket=/dbcm/run/mysqld.sock` on a volume whose `run/` is 0750 `999:999`, the entrypoint's temporary init server and `docker_process_sql` use that socket, and the healthcheck/`mariadb` CLI inside the container still work (the image's client default is `/run/mysqld/mysqld.sock`).
2. The donor's `wsrep_sst_mariabackup` connects as `mysql@localhost` through the moved socket; SST and IST complete as in E1.
3. The agent (root, host network, volume base bind-mounted) can connect to the socket inside the volume across the container boundary, and MariaDB reports the connection as `localhost` so `'dbcm_monitor'@'localhost'` matches.
4. `CREATE USER IF NOT EXISTS`/`ALTER USER`/`REVOKE`/`GRANT` on the bootstrap node replicate to joiners by SST in 11.4.13; `SHOW GLOBAL STATUS LIKE 'wsrep_%'` works for a USAGE-only account; `REQUIRE SSL` over the unix socket is not used by default (assumed to fail without TLS on the socket).
5. mariabackup with only `RELOAD, PROCESS, LOCK TABLES, BINLOG MONITOR` takes a streamed backup with `--galera-info` over TCP from the job (host `%`), reading the datadir mounted read-only as uid 999; `SHOW CREATE ROUTINE` is accepted by 11.4 for the logical export.
6. The mysql UID/GID is 999:999 in the amd64 image as well.
7. The job image builds; the inherited `VOLUME /var/lib/mysql` creates an anonymous volume per job task; whether Swarm removes it with the task (otherwise scoped cleanup must) is unknown.
8. `init-volume-dirs` on the real Docker local volume (`type=none,o=bind`) produces directories the container sees with the same numeric owner (no user namespace remapping on the hosts).
9. The global agent service can be updated to mount per-cluster root secrets without disrupting running operations (rolling agent restart; fencing and idempotent steps should cover it).

## Consequences

- Existing clusters created with the earlier spec have no `--socket` and no `run/` directory; changing their spec is an update that restarts nodes and needs `init-volume-dirs` first (no migration exists; there are no production clusters yet).
- The manager still has to: generate and create the account secrets, attach the root and backup secrets to the agent service, fill `Cluster.Accounts` from settings, and render the backup option-file secret.
