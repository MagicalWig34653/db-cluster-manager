# ADR 0025: Image update service (Watchtower-style, owned services only)

Status: **Implemented with fakes only; no registry, Swarm or VM used**, 2026-10-28. Implements the owner decision of 2026-10-27 ([ENTSCHEIDUNGEN](../ENTSCHEIDUNGEN.md)): Docker updates may be executed through the Docker socket in the manner of Watchtower. Requirement X16. Builds on [ADR 0019](0019-docker-engine-update-plans.md) (engine upgrades stay reviewed plans), [ADR 0015](0015-ai-assisted-vulnerability-response.md), [ADR 0023](0023-os-patch-management.md) and [ADR 0024](0024-agent-runtimes.md).

## Scope

In: image updates of **managed services** (pull a newer tag or digest, update the Swarm service, wait for the health gate, roll back on failure). Out: the Docker engine itself (ADR 0019, reviewed plans only), containers or services the manager does not own, and Galera clusters (they go through the rolling or minor-upgrade planner).

## Decision and alternatives

| Question | Chosen mechanism | Alternative and reason |
| --- | --- | --- |
| How candidates are found | **Manager-scheduled check on the leader** (`ImageUpdateScheduler`, one registry read per service and interval) plus an on-demand check. Registry access reads tags and manifest digests over the OCI distribution API v2 (`registry.External`, credentials from the sealed registry store, sent only to the registry host and its token realm). | Watchtower-like polling inside a sidecar needs its own Docker socket access, its own credentials and runs on every node; it would bypass the manager's authorization, approval and audit. Registry events or webhooks need an inbound endpoint reachable by registries and a secret per registry; they remain a possible later trigger for the same `Check`, not a replacement. |
| How updates run | Through the **existing approval-gated service update operation** (`service/update`): the agent's `update-service` command with the Swarm `UpdateConfig` and `RollbackConfig` from the policy strategy, `await-service`, the service-healthy gate, journaled with `executedBy` runtime (ADR 0024). The image service adds a reviewed plan, a policy and a digest approval on top and never talks to Docker itself. | A new agent command that pulls and recreates containers would duplicate allow-list, ownership and rollback logic. The Docker socket therefore stays behind the container agent's existing allow-listed executor; the new feature adds no socket access path (the "opt-in flag" is `manager.imageUpdate.enabled`, default off). |
| Scope | Only services carrying this installation's ownership label (`dbcm.installation`). A service of another installation, without the label, or any foreign service is invisible and refused (404). A foreign service is considered only with the explicit label `dbcm.image-update=opt-in` **and** an inventory entry, and then only for notifications (route `report-only`, cannot be approved). | Watchtower's default of updating every container was rejected: it would touch unrelated objects. |
| Policies per service | `manual` (default; no scheduled check), `notify` (scheduled check, reviewed plan, notification, a person approves and applies), `auto` (the policy approves eligible plans itself and applies them inside a maintenance window). Tracks: `digest` (same tag, new digest), `patch`, `minor`, `major`. | One global mode: too coarse; a web server and a database need different rules. |
| Tag rules | A candidate keeps the variant suffix (`-alpine`), the `v` prefix and the precision of the current tag (`11.4` moves to `11.5`, not to `11.4.2`); pre-releases, `latest` and non-version tags are never candidates; versions never go down. Databases (service type `galera` or a repository name containing a database name) never follow `major`. | Semver-only parsing would miss real tag schemes; refusing everything unusual is the safe default. |
| What `auto` may do | Only registry candidates of kind `digest` and `patch`, and `minor` for non-databases; never `major`, never `built` images, never rollbacks, never database minor jumps, never Galera, never foreign services; a maintenance window is mandatory and re-checked at apply time; an auto plan whose policy is no longer `auto` is not applied. Everything else becomes a proposed plan for a person. | Allowing minor jumps for databases was rejected: they change on-disk formats. |
| Galera | Plans exist (route `planner`) so the operator sees the candidate, but approve and apply are refused (409 `policy_conflict`); the rolling or minor-upgrade planner is the only way. | Updating the Galera service image directly would bypass quorum and recovery rules. |
| Digest pinning | The applied image is `repo:tag@sha256:...`; the baseline digest of the followed tag is recorded in the service state and moves only after a successful update. The first check of an unpinned tag only records the baseline (Swarm resolved the tag at deploy time and the manager cannot know which digest runs). A target that was declined, failed or rolled back is not proposed again by the scheduler; an operator check forces it. | Following a tag without recording digests cannot tell a rebuilt tag from the running image. |
| Health gate and rollback | The plan's strategy becomes Swarm `UpdateConfig` (`failureAction: rollback`, monitor period, order, parallelism) and `RollbackConfig`; Swarm restores the previous spec when a new task fails. The operation's `await-service` step reports `rollback_completed`; the plan then records `rolled_back` with an automatic rollback record. A manual rollback is a separate plan (`rollback` kind, own approval, never automatic) that uses the manager's rollback to the previous spec. A wait limit (`waitMinutes`) ends an operation without result as `failed` with an unknown outcome; nothing is rolled back blindly. | A manager-side rollback loop would race with Swarm's own. |
| Approval and permissions | Digest-bound approval of the plan (like patch plans). Applying starts the service update operation as the caller and approves it with the caller's own permission (`update` on the service), so a user without that permission fails closed; automatic plans act as the manager system subject. API resource `image_update`: viewer read, operator read and operate (check), administrator everything. | A separate approval path would bypass the service authorization. |
| Windows | Reuse `patch.Window` (days, start, duration, zone, overnight). | A second window model. |
| Secrets | Registry credentials come only from the sealed registry store; registry and agent error text is redacted (bearer, basic, password, token patterns) and truncated before storage, notification or log. No secret enters plans, journal, notifications or API answers. | |
| Notifications | `imageupdate.candidate`, `applied`, `rolled_back`, `failed`, `check_failed` (once per distinct error), `policy_changed` through the existing monitoring dispatcher. | |
| Vulnerability link | `POST /image-updates/offers` takes a succeeded image build job (X08) and creates `built` plans for every service in scope that runs the same repository. They are never auto-approved, whatever the policy. The automatic hand-off from a finished vulnerability build is **not wired** (the build runs asynchronously; see limits). | Auto-offering and auto-applying a patched build would make the AI/vuln flow a rollout path without a person. |
| Leader and recovery | Metastore-backed records, leader term as fence, `RecoverInterrupted` marks plans left `running` by a previous leader as failed with an unknown outcome (the apply journal is in memory) and sends nothing. | |

## Known limits

- Fakes only: no registry, Docker, Swarm or VM; the registry client is the existing one tested against an `httptest` registry. Multi-arch manifest lists are resolved by the registry's digest header only; per-platform digests are not compared.
- Updates need the digest in the spec: the service update replaces the image string with `tag@digest`; services created from a digest-less tag therefore change their spec string on the first update.
- The manager does not read the digest a running Swarm service actually uses; the baseline is the registry's answer at the first check.
- Replica count, placement and mounts cannot change through this feature (the agent's update-service keeps them).
- The automatic hand-off from a vulnerability build to an offer, a UI, registry webhooks and per-platform digest checks are not built. Only the container agent runtime executes updates.
