# ADR 0027: Fresh-server bootstrap profile

Status: **Implemented; simulated host in the tests, plus lab E17 (2026-10-31) on a real Debian 12 and AlmaLinux 9 VM driven by `cmd/bootlab` (service, SSH runner and host key probe real; HTTP API, UI wizard and manager wiring not run)**, 2026-10-29. Implements part 1 of the owner additions of 2026-10-29 ([ENTSCHEIDUNGEN](../ENTSCHEIDUNGEN.md)): the manager can onboard completely fresh servers the owner administers. Requirement X18. Builds on [ADR 0018](0018-ssh-cluster-provisioning.md) (SSH plans, pinned host keys, digest approval), [ADR 0023](0023-os-patch-management.md) (native agent install), [ADR 0024](0024-agent-runtimes.md) (two agent runtimes, capabilities) and [ADR 0010](0010-agent-transport-and-enrollment.md) (enrollment tokens).

## Scope

In: OS detection and a support matrix, a read-only preflight, a bootstrap plan of ordered reviewed scripts, a step executor over the existing `CommandRunner`, an in-memory draft service, REST API, a UI wizard. Out: cloud APIs, network scanning, host discovery, installing anything on a host that is not named by the operator, k3s execution (stays a preview, ADR 0018), Windows/macOS/BSD, and any real-host run (needs the lab and the owner's go).

## Decision

| Question | Chosen mechanism | Alternative and reason |
| --- | --- | --- |
| Support matrix | Data in code (`provision.SupportMatrix`): Debian 12/13, Ubuntu 22.04/24.04, AlmaLinux 9/10, Rocky 9/10, Alpine 3.19-3.22, amd64 and arm64. The preflight reads `/etc/os-release`; a system outside the matrix is a blocking finding, never a best effort. Alpine (OpenRC) gets the Docker engine from its own repository only; native agent, firewall and unattended upgrades are refused there because they need systemd, ufw/firewalld and apt/dnf. | A generic "any Linux" mode would run unknown package managers with root rights. |
| Preflight | One fixed read-only script prints `key=value` lines: OS, version, architecture, CPUs, memory, free disk, time sync, systemd, privilege (root or passwordless sudo), package manager, Docker version, Swarm/k3s membership, native agent present and whether this tool installed it, restic, sshd settings (`sshd -T`), whether the service user exists, busy ports of the selected profile, other server software. Blocking: unsupported OS or arch, no root/sudo, below 1 GiB memory or 10 GiB disk, busy ports, a foreign agent, existing Swarm/k3s membership (refused as in ADR 0018, no plan at all). Warnings: an existing Docker engine (kept, not upgraded), other server software, thin memory, Docker bypassing ufw/firewalld. | Probing by installing helper tools first would change the host before review. |
| Baseline hardening | Always: base packages (curl, sudo, certificates, gnupg), time synchronization only if the clock is not synchronized, a service user (default `dbcm`) with a locked password and a validated sudoers drop-in, and a **read-only sshd audit** that reports root login, password authentication and the port and changes nothing. Opt-in: firewall (ufw on Debian/Ubuntu, firewalld on AlmaLinux/Rocky; the SSH port found by the preflight and the profile's ports are allowed **before** the firewall is enabled) and unattended security upgrades (unattended-upgrades, dnf-automatic). | Changing sshd as part of the baseline is the classic lock-out; here it is a separate phase. |
| Container runtime | `docker` or `none`. Docker comes from the vendor repository (`download.docker.com`, apt or dnf), with the repository key downloaded over HTTPS and **its fingerprint compared with the pinned `DockerKeyFingerprint` before it is trusted**; a mismatch aborts. An already installed engine is kept as it is. | The convenience script `get.docker.com` runs unreviewed code from the network; distribution packages lag. |
| Agents | Native agent through the reviewed install script of ADR 0023 (adapter `patch.BootstrapAgentScripts`: pinned release URL and SHA-256, systemd unit, mode `report` or `apply`, restic paths), enrolled with a one-time token delivered on stdin; container agent as a manager action that deploys the Swarm service of ADR 0024 (no script on the host). Patch and restic are capabilities of the native agent and need it. | A second install path would drift from the reviewed one. |
| Cluster | Swarm `init` or `join-manager|join-worker` with the commands of ADR 0018; the join token is a write-only draft secret, passed on stdin. k3s is rendered but blocked (execution disabled). | Executing k3s over SSH has no evidence yet. |
| Step shape | Every step is a shell script with a header marker `# dbcm-bootstrap <plan> <step> run|check|cleanup`, a SHA-256 digest, a read-only **check** script (`dbcm:done=yes|no`), an idempotency guard (a state marker in `/var/lib/dbcm-bootstrap` plus the real condition) and a **cleanup** script. Cleanup undoes only what the step added (repository file, sudoers drop-in, firewall rules it opened, sshd drop-in); it never prunes, force-removes, purges or deletes data, and says so where something is intentionally kept (Docker engine, users, packages). The cleanup plan is output for the operator; the product does not run it. | A global rollback would need destructive commands. |
| Journal, resume, fencing | The executor journals every step in `opjournal` under the leader term (`Begin`, `StartStep`, `FinishStep`). A step already `Succeeded` is skipped; before running a step its check runs and a satisfied step is marked done without the script. A mutating script with an unknown outcome leaves the step `Unknown` and stops; resume (a newer term `Adopt`s) re-checks it. A stale term is refused by the journal (`ErrNotOwner`). | Re-running everything and relying on idempotency alone would hide partial states. |
| Host key pinning | `Draft` reads the host key of that one host without authenticating (`SSHHostKeyProbe`) and shows type and SHA-256 fingerprint. **No credential is used until the operator types the fingerprint.** A mismatch cancels the draft and wipes the credentials before any login. The accepted key is pinned for all later connections (`SSHRunner` offers only the pinned key type); a changed key stops the run. | Trust on first use would accept a man in the middle. |
| Credentials | Password or private key are write-only, held in memory in the draft only, never in argv (stdin and the SSH library only), logs, the journal, the plan or any API response; a root password is accepted only here and only as the bootstrap login. They are wiped on completion, cancel, a failed fingerprint and after one hour without activity (`ErrCredentialsExpired`; supply them again). A manager restart drops all drafts. | Sealed storage of a root password would keep the most dangerous secret. |
| Lockdown | Dedicated key, root-login switch and their steps carry `gate: lockdown` and a **second digest** approved by a second call after the main phase finished. Order: install the public key for the service user; verify a login with the key and `sudo` over a **new** connection; seal the private key in the manager (if sealing fails nothing is locked); write a `PermitRootLogin no` drop-in in `sshd_config.d` after `sshd -t`; arm a detached revert that removes the drop-in after 180 s; reload; **confirm over a new dedicated-key connection** which cancels the revert. If the confirmation fails the host reverts on its own and the operator can still log in as before. Refused if sshd does not include `sshd_config.d`. Password authentication is never changed by this tool. | Editing `sshd_config` directly or disabling root without a verified second path is the lock-out. |
| API and permissions | `/bootstrap/*` (draft, fingerprint, plan, approve, approve-lockdown, credentials, run, status, cancel): **administrator only** (`settings` update with the administrator guard), 503 until `Config.Bootstrap` is set, secrets never echoed. Digests are checked by the service, not the client. | Operator access would let a lower role obtain root on new hosts. |

## Known limits

- Simulation only: the tests use an in-memory host that recognizes the step markers and applies state transitions. It does not interpret shell. The scripts are only syntax-checked with `sh -n`; none has executed on a real system, so quoting, package names, repository URLs, service names (`ssh` versus `sshd`), the `ufw`/`firewalld` commands, the Docker key fingerprint constant and the revert timing are untested assumptions.
- The Docker key fingerprints were checked against live downloads in lab E17: the apt key (`DockerKeyFingerprint`) on Debian 12 and the **different** rpm key (`DockerRPMKeyFingerprint`) on AlmaLinux 9.8. Before E17 one constant was used for both and every dnf bootstrap failed. E17 also fixed the preflight memory parser (mawk printed 4.12e+09) and the base-packages check (no gpg on a fresh Debian). See [E17 bootstrap results](../../tests/p0/results/e17-bootstrap.md); Ubuntu, Rocky, Debian 13 and Alpine and the native-agent and cluster-join steps are still unrun.
- Drafts and the journal are in memory: a manager restart loses drafts and credentials (by design); the executor is resumable within the process lifetime. A persistent journal and a leader-fenced runner integration (as ADR 0018) are not wired. The `Bootstrap` backend is not constructed by the manager yet (routes answer 503), and the enrollment-token source and the container-agent deployment hooks are interfaces without a production implementation.
- A password login needs an SSH server that allows it; many fresh images permit root only by password or key.
- One host per bootstrap. No concurrency control for several drafts on the same host.
- k3s is blocked; Alpine has no native agent, firewall or unattended upgrades; no FIPS/SELinux/AppArmor profile work; a firewall in front of Docker does not filter published ports.
- The lockdown revert uses a detached `sleep` on the host; a reboot within 180 s drops it (then the drop-in persists, which is the locked-down state, and the dedicated key must work).
