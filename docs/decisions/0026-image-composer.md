# ADR 0026: Image composer (point-and-click image recipes)

Status: **Implemented with fakes only; no VM, registry, network or real build used**, 2026-10-29. Implements the owner addition of 2026-10-29: the contents of a service image are assembled by selecting components (for a web server: distribution/base, nginx with version and settings, PHP with version, extensions and php.ini settings, further components), with variants per distribution. Requirement X17. Builds on X08 (image build service, approval flow), X04 (web server composition, `internal/imagebuild`), X13 (vulnerability inventory) and [ADR 0025](0025-image-update-service.md) (rollout of built images stays a reviewed update).

## Scope

In: a versioned component catalog as data, a typed recipe, validation with allow-listed typed settings, a deterministic recipe-to-Dockerfile/context generator, a reviewed preview, REST API, a UI page and the hand-off to the existing build service. Out: free-form Dockerfiles, arbitrary shell, third-party package repositories, PECL/source builds, multiple sites per image, image signing, and the real SBOM/scan (the build service still records `not_generated`; the generator already emits the package list as their input).

## Decision

| Question | Chosen mechanism | Alternative and reason |
| --- | --- | --- |
| Where the choices live | **Catalog as data**: `internal/imagecompose/catalog.json`, embedded with `go:embed`, `schemaVersion` 1, decoded with unknown fields rejected and self-validated at load (unique ids, every matrix entry refers to an existing release and architecture, every default satisfies its own schema, strings need a pattern and length limit). The catalog has a `version` that enters the recipe digest. Every catalog is marked `evidence: unverified` until upstream documents or a real build confirm it; the validator refuses any other value. | Hard-coded Go tables (as `imagebuild.Catalog`) cannot be reviewed or extended without code; a catalog fetched from a remote source would add a supply-chain path and was rejected for the first version. |
| Compatibility | A **matrix** `component version x distribution release x architecture` with per-entry package names, constraint, dnf module streams and (PHP) binary/prefix. A version is selectable only where an entry exists; features (PHP extensions) are per distribution family. Variants: for any recipe the API reports per release whether the same choice is possible, the problems, and the newest version of every selected component there. | A full cross product with failures at build time was rejected: the user would find out minutes later. |
| Settings | Typed, **allow-listed fields** per component: `bool`, `int` (min/max), `enum`, `string` (mandatory regex and max length; no free text), plus a target (`ini`, `pool`, nginx). Unknown keys are refused, values are coerced to canonical types, defaults fill the rest, preconditions (`needs`, `needsFeature`) refuse settings that cannot apply (for example `opcache.*` without the opcache extension). Cross-field rules (`post_max_size >= upload_max_filesize`, `memory_limit >= post_max_size`, FPM spare-server ordering) are checked in code. All findings are returned together with a path (`components[php].settings.pm`) so a form can show them. | A "custom snippet" field (as in `imagebuild`) was **not** carried over: a deny-list is not a parser. Anything outside the schema is a catalog change, not a user input. |
| No shell | Values reach only generated configuration lines (`key = value` from a validated type) and package names from the catalog. No user text enters a `RUN`, `ENV`, `ARG`, `ENTRYPOINT` or label argument except the validated image name, which is quoted. | Free-form Dockerfile: maximal freedom, but no validation, no reproducibility notes, no variants and a direct injection path; rejected. Buildpacks (Cloud Native Buildpacks): good for application source, not for choosing nginx/PHP versions and extensions, and they require builder images and a lifecycle runtime on every build host. Nix: strongest reproducibility, but a different packaging world, large closure sizes and a steep operator learning curve; a possible later back end behind the same recipe, not the first one. |
| Generator | `Catalog.Generate(recipe)` is a pure function (no clock, randomness, network or registry lookup): Dockerfile and context files sorted by path, package lists sorted, map iteration never reaches the output. Golden-file tests per distribution family pin the exact output; a determinism test renders repeatedly. The output type is `imagebuild.Rendered`, so the existing builder runs it unchanged. | Templates evaluated at build time would make the preview differ from the built context. |
| Hardening defaults | Base pinned by digest (a floating tag is refused). Non-root user `app` (uid/gid 10001), `USER` before the entrypoint. nginx on port 8080, pid and temp paths in `/tmp`, server tokens off, security headers on, dotfiles denied. PHP: `expose_php`, `display_errors`, `allow_url_fopen` off, `allow_url_include` off and `cgi.fix_pathinfo=0` fixed (not configurable), cookies `httponly` and strict sessions on, errors to stderr, `clear_env`. Packages only from the distribution, no recommends/docs, caches removed in the same layer, no `curl`/`wget`/`ADD`/`ARG`, no secrets. The Dockerfile runs `nginx -t` and `php-fpm -t` on the final configuration during the build. | Opt-in hardening was rejected: the defaults are what most users keep. A hardening toggle can be added to the catalog per setting; fixed lines are deliberately not toggles. |
| Single-process rule | Exactly one **main** process per image (`process: main`); PHP is a **companion**: with nginx it is started by a small generated entrypoint that backgrounds `php-fpm` and `exec`s nginx (no supervisor, no cron, no sshd). Without nginx, `php-fpm -F` is the single main process and listens on 9000 for an external web server. A second main component is refused. The warning states that a dead PHP-FPM is not restarted (nginx answers 502) and that the health check must cover it. | A supervisor (s6, supervisord) inside the image was rejected: it hides failures from Swarm, adds a second init and widens the attack surface. A sidecar PHP service is the cleaner topology and stays possible with the `fpm` role. |
| Recipe digest | `sha256` over canonical JSON of the **normalized** recipe (defaults applied, lists sorted, canonical types) plus the catalog version and a generator version. Equal intent gives an equal digest; a changed catalog or generator is visible. It is the build job's `specHash` and is written as the image label `dbcm.recipe-digest`. | Hashing the raw request would make field order and explicit defaults change the digest. |
| Reproducibility notes | The preview states what is and is not reproducible: the generated Dockerfile and context are byte-identical for the same recipe, catalog and generator version; the image bytes are identical only while the base digest and the distribution repositories are unchanged, because package patch versions float within the major.minor constraint (apk `~=`, apt `=X.*`, dnf module streams). Pinning to exact package versions would need repository snapshots (not built). | Claiming "reproducible builds" without that sentence would be misleading. |
| Build, approval and permissions | The composer never builds itself. `POST /image-composer/builds` renders **server side** from the recipe, then uses the existing plan/approval flow (`Service.PlanRendered` / `StartRendered`: a plan digest binds recipe digest, context hash, platforms and target; a changed recipe, target or platform needs a new approval; the context hash is re-verified, so a tampered context is refused). The client never supplies a Dockerfile. Jobs carry `source: composer` and the normalized recipe. Permissions: viewer reads the catalog (`image_build` read); operator and administrator preview (`image_build` create); **building and planning a build need `image_build` update, i.e. the administrator**. Denials are audited. | Letting operators build was rejected: a build pushes to a registry with a stored credential. |
| SBOM and scan | The preview lists the packages (component, name, constraint) and dnf modules the image will contain, which is the intended input of the SBOM and of the X13 inventory. The build service still records the SBOM as `not_generated`; no scan runs. The vulnerability flow can already rebuild a recipe with a newer base digest through the same plan/approval path, and ADR 0025 rolls a built image out as a reviewed update. | Generating an SBOM inside the generator would claim a result the build has not produced. |

## Known limits

- Fakes only. The catalog is unverified: package names, versions and dnf module streams were written from knowledge and never checked against live repositories or built; the build is the check. Some entries are probably wrong or stale (especially `almalinux` module streams and the Ubuntu/Debian PHP versions).
- No image has been built from a generated recipe; the `RUN nginx -t`/`php-fpm -t` lines have never executed. The entrypoint behaviour (backgrounded PHP-FPM, `exec nginx`) is untested in a container.
- Distributions are the four above (Alpine 3.20, Debian 12, Ubuntu 24.04, AlmaLinux 9). Official upstream images (`nginx`, `php`) are not used as bases; the distribution's own packages are.
- PHP extensions are a curated list of 16, no PECL or source builds. nginx modules, TLS certificates, multiple sites, PHP-FPM pools beyond `www` and cron jobs are not selectable.
- The manager process does not wire `ImageComposerBackend` yet; the endpoints answer 503 until it is constructed with a build service. The web page works against the development mock server only.
- Packages float within their constraint; exact pinning needs repository snapshots.
- Cross-field rules cover PHP sizes and FPM spare servers only.
