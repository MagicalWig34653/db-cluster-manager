# ADR 0024: Explicit agent runtimes and capability routing

Status: **Implemented with fakes and loopback listeners; not run on VMs**, 2026-10-27. Implements the owner decision "Native agent for further features" in [ENTSCHEIDUNGEN](../ENTSCHEIDUNGEN.md). Extends [ADR 0010](0010-agent-transport-and-enrollment.md), [ADR 0022](0022-native-restic-host-backups.md) and [ADR 0023](0023-os-patch-management.md); changes no safety rule of the Galera, recovery or backup flows.

## Decision and alternatives

| Question | Chosen mechanism | Alternative and reason |
| --- | --- | --- |
| One agent or two runtimes | Two runtimes stay: the **container** agent (Swarm global service, Docker API, default for Swarm objects and Galera steps) and the **native** agent (systemd service, host paths, no Docker socket). Each reports `runtime` and a capability list. | A single agent with the Docker socket on the host would give patch and restic root plus Docker control in one process and tie package updates to Docker availability. A single native agent for everything would drop the Swarm-managed rollout of the container agent and give Docker control to a host service. Two runtimes keep the blast radius of each function separate; the price is two deployments and an explicit mapping. |
| Capability names | `docker-objects`, `galera-steps`, `restic`, `patch`, `host-maintenance`, `diagnostics`. The last two are reserved: no agent claims them and no step maps to them yet. | Free-form strings would let a typo or a compromised agent invent routing targets. |
| Who may claim what | `internal/agentrt` holds the allowed set per runtime. Container: `docker-objects`, `galera-steps`, `restic`, `diagnostics`. Native: `patch`, `restic`, `host-maintenance`, `diagnostics`. A report outside the set is a **mismatch** and is rejected. | Trusting the report would let a container agent announce `patch` and attract root-level package commands. |
| Where it is reported | In the enrollment and renewal request (`runtime`, `capabilities`; a mismatch is refused with 400 `runtime-mismatch` before the token is consumed), and as response headers `X-Dbcm-Agent-Runtime` and `X-Dbcm-Agent-Capabilities` on **every** agent answer (command endpoint, patch endpoint, error answers). The manager validates each report, stores it per host (`HostRecord.AgentReports`) and, on a mismatch, stores `AgentReportError`, keeps the previous valid report and refuses the host for routing until a valid report arrives. | A separate hello endpoint adds a round trip and a state that can go stale. Headers on every answer refresh the record for free; the report is mTLS-authenticated like the command. |
| Agent-side enforcement | The executor refuses (invalid command, no step record) every command whose capability its own report does not list, independent of what the manager decided. A native agent has no Docker client at all. | Manager-only routing would make a routing bug an execution bug. |
| Routing | One explicit table in `internal/agentrt` maps every step type to one capability and an ordered runtime list. Docker object steps and Galera steps: container only. Patch (`patch/report`, `simulate`, `apply`, `reboot`, `deny-list`): native only. Restic: native first, then container. `host-maintenance` and `diagnostics`: no step yet. A kind not in the table is refused; a test keeps the table equal to the agent's command kinds. | Deriving the runtime from "which agent answers" hides moves between runtimes. |
| No silent fallback | `Select` takes the first listed runtime whose current report has the capability. If none does, it returns an error naming the required capability and runtime and what the host reports. Restic with a native agent that lacks the `restic` capability uses the container agent only because the table lists it explicitly; patch never falls back. API: `POST .../backups` answers 409 `agent_runtime_unavailable` and starts nothing. | Falling back to "whatever is there" would, for example, run package updates through the wrong trust boundary. |
| Hosts without a report | A host whose agents never reported (build before this ADR) is treated as a legacy container agent with `docker-objects` and `galera-steps` only. Restic and patch are refused until the agent reports. | Granting new capabilities to unreported agents would be a silent change. |
| Evidence of execution | The agent stamps `runtime` on each result; the manager checks it equals the selected runtime (a different runtime is an error). The runner view has `runtime` per step; the journal timeline detail reads `[executed by runtime=... host=...]`; the API operation has `executedBy` (step, command, host, runtime, agent identity); each executed step writes an audit record (`operate` on the host, change text with operation, step, runtime and agent identity). Patch plans and patch hosts carry the runtime. Host sources show the runtime that would execute them (`runtime`, `runtimeNote`). | Logging only the target host cannot tell which of two agents on one host acted. |
| Restic on the native agent | `agent patch` gains `-restic-allow-path` (repeatable) and `-restic-secrets-dir`. With at least one path it reports `restic`, builds the same executor and serves the same fenced `restic-*` commands on its mTLS server (path `/v1/commands`) next to `/patch/v1/command`. Allow-list, protected paths (secrets dir, Docker socket), secret files as regular files, `--overwrite never` restores and the repository probe are the code of ADR 0022, unchanged. | A second restic implementation for the native agent would duplicate the security-relevant code. |
| Installing it | The SSH install plan of ADR 0023 (reusing ADR 0018) accepts `resticPaths`. The unit gets the `-restic-allow-path` flags and `-restic-secrets-dir /etc/dbcm-patch/secrets`; the script creates that directory (mode 0700, owned by `dbcm-patch` in report mode) and refuses without the `restic` binary; the preflight reports `restic` and `ssh` availability and the plan is refused when restic is wanted but missing. The report-mode unit runs as `dbcm-patch`, so it can read only what that user may read (see guide 24). | Installing restic from the manager would add a package-manager write to a read-only preflight. |

## Known limits

- **One identity slot per host.** The enrollment record holds one agent serial per host. The container agent and the native agent of one host share the host ID and URI SAN; enrolling the second one supersedes (and revokes) the certificate of the first. Running both on one host is therefore **not yet supported end to end**; the routing, reports and tests treat them as two runtimes, but a per-runtime identity (one serial and one URI SAN per runtime) is future work. Until then each host should run one of them, or the second must use a different `-host-id` mapping decided by the operator.
- Fakes and loopback only: no VM, no real restic on the native agent, no real systemd install. `host-maintenance` and `diagnostics` are names only.
- Report-mode native agents run unprivileged and cannot read root-owned data; use the apply-mode (root) install for whole-host backups or grant the `dbcm-patch` user read access to the allow-listed paths.
- The UI shows a runtime badge per host and a gap note; per-function and per-operation display is missing (the API has it).
- API error bodies carry only the stable code; the reason is in `runtimeNote` of the host source and in the manager log.
