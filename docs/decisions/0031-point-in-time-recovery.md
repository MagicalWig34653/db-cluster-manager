# ADR 0031: Point-in-time recovery through archived binary logs

Status: **Proposal implemented; real tools exercised once in the lab (E15), the manager path with fakes only**, 2026-10-31. Builds on the [ADR 0009](0009-cluster-backup-method.md) amendment (binlog archive library) and [ADR 0021](0021-backup-targets-copies-and-metastore-backup.md) (approval-gated restores, no promotion).

## Confirmed requirements

[KONZEPT.md](../KONZEPT.md) B02: optional point-in-time recovery from continuously archived change logs. [AGENTS.md](../../AGENTS.md): restores go to new targets, nothing is overwritten in place without an explicit product-level approval, full-cluster recovery needs approval, and no cross-cluster copy is promoted automatically.

## Decisions (proposed)

1. **Binary log is a cluster option, off by default.** `binlog: true` at cluster creation adds `--log_bin=<datadir>/dbcm-bin --log_slave_updates=ON --binlog_expire_logs_seconds=1209600` to every node (`galera.Cluster.Binlog`). `log_slave_updates` makes every node's log hold the writes applied from the other nodes, so the backup's source node has the whole history. Files expire after 14 days. The option is stored with the cluster spec; changing it on an existing cluster is not supported yet (it would be a rolling restart with its own approval). Alternative considered: always on. Rejected: extra disk and write load for clusters that do not want PITR (B02 says optional).
2. **Archive job, per full backup, on the backup's source node.** `dbcm-job backup --tool=binlog-archive` (agent tool `binlog-archive`) mounts the source node's volume read-only like the physical backup, rotates the log (`FLUSH BINARY LOGS`, needs `RELOAD`, which the backup account has) and encrypts every closed file from the backup's position on to the backup target: one archive per file (`ArchiveBinlog`: sealed stream, keyed digests, range bound into the authenticated header, manifest last). The job reads the existing archives of that backup first and continues the chain; with nothing new it succeeds without writing. Closed files are read straight from the volume and checked by walking the event headers (the chain must end exactly at the file size), which gives the first and last event time without a MariaDB tool. A file the chain needs but the node no longer has, or a chain with a gap, fails the job with the reason instead of archiving across the gap. `POST /clusters/{id}/binlog-archives` starts it for the newest completed backup with a binlog position. Alternatives: `mariadb-binlog --read-from-remote-server` (needs the replication privilege on the backup account and a live connection per file; rejected for now), a continuous sidecar (a long-lived service per node; rejected: more moving parts, and the archive interval would still be a policy choice). No scheduler yet: archive runs are started through the API or UI (limit below).
3. **Chain and gap rules are one function.** `binlogChain` accepts only a contiguous chain that starts at the base backup's file and offset (sequence 1, consecutive file numbers, one history, continuous time ranges, identities equal to the base). `ResolvePITR`, `CoverageOf`, the proposal, the planner and the replay job all use it, so the job re-derives what the plan promised and refuses anything else (a skipped file, a different base, a stop time past the last archived event). A different source node (replaced, failed over) ends the chain: the plan refuses and a new full backup is needed. GTID-based continuation across nodes (`wsrep_gtid_mode`) is not implemented.
4. **Time semantics.** The target is a UTC second; the replay applies every event up to and including that second (`mariadb-binlog --stop-datetime` is exclusive, so the plan passes the next second). Event times are second-precise and not assumed monotonic, so a time at or after the last archived event is **not covered** (the next file may hold events of the same second). The job container runs with `TZ=UTC`.
5. **Restore is the inspection restore plus a replay, into a NEW instance.** `POST /restores/inspect` with `pointInTime` picks the newest backup that ended before the time and whose archive reaches it (`GET /clusters/{id}/pitr-proposal` answers the same question read-only and names the reason when it does not). The plan adds, after the instance is created: the replay job (agent mode `binlog`, `run-restore`, approval-gated like every restore command), its completion gate, removal of the job and removal of the replay secret. The approval digest covers all of it. The replay job refuses any target that is not an inspection service (`dbcm-inspect-` prefix; also checked by the agent). There is no in-place path and no promotion; adopting the restored data in production remains a separate, explicitly approved procedure that this ADR does not provide.
6. **Replay account.** Applying row events needs write privileges, which the read-only inspection account lacks. A point-in-time session's init file also creates `dbcm_replay` with a random password that exists only in the init file and in the replay option-file Swarm secret; the replay job drops the account when it succeeds and the plan removes the secret. The account is reachable only on the session's isolated network. If the instance restarts, the init file recreates the account with a password nobody holds any more. Alternative: replay through the unix socket in the instance's container (needs an exec path; rejected, the agent never execs in database containers).
7. **Retention.** Archives are found by name (`<cluster>-<backup>-l*`) and deleted together with, and before, their base backup; a damaged archive cannot keep its base alive.

## Evidence

- Go unit and in-process tests: chain and gap cases, tampered ranges and streams, planning with approval on every destructive step and acceptance by the real agent executor, job helper with a fake tool runner (archive: closed files only, incremental, gap, truncated file, wrong node; replay: order, refusal of what the plan could not produce, wrong key, tampered segment, failed tool), manager proposal/start/teardown/retention, API routes and permissions, UI client and form logic.
- Lab E15 ([results](../../tests/p0/results/e15-pitr.md)): real `dbcm-job`, MariaDB 11.4 Galera on three lab VMs; see the results file for what passed and what did not run.

## Consequences and limits

- The manager, agent and UI path of a point-in-time restore has not run against real Swarm services; E15 drove the real job helper with `docker run`.
- No scheduled archiving: the recovery point is the last archive run. Run it at least every 14 days or the job reports a gap.
- One source node per backup; node replacement before the archive is complete loses the chain. No GTID continuation.
- The binary log setting is fixed at cluster creation; existing clusters cannot enable it yet.
- Selective table-level PITR and restore into a different cluster's identity are not covered.
