# ADR 0029: Guided Galera recovery from the zero cluster UUID

Status: **Implemented with fakes only (2026-10-30); no VM was used.** The manual procedure it automates was verified by hand in lab E12 ([results](../../tests/p0/results/e12-recovery-autofailover-rolling.md)); the product operation itself has not run against a real cluster. Implements owner decision 1 of 2026-10-30 ([ENTSCHEIDUNGEN](../ENTSCHEIDUNGEN.md)), which is the product-level approval AGENTS.md requires for full-cluster recovery. Extends the guided recovery of [ADR 0004](0004-swarm-ownership-and-local-storage-identity.md) (A06) and builds on the approval flow, the operation journal and the health model.

## Problem

After a total power loss the Galera component can re-form with `wsrep_cluster_state_uuid = 00000000-...` (E9, E12). Every `grastate.dat` then holds the zero state and `mariadbd --wsrep-recover` answers `0000...:N`. The full-outage diagnosis needed a real UUID and answered `no_candidate`; the product had no path from this state. E12 repaired it by hand three times: highest local seqno bootstraps with a new state UUID, the others take SST, nothing committed before the power loss was lost.

## Decision

| Question | Chosen mechanism | Alternative and reason |
| --- | --- | --- |
| Shape | Two journaled, approval-gated operations sharing one snapshot name: `galera/zero-uuid-prepare` (approval, stop all, await stopped, verify identity markers, snapshot every data directory) and `galera/zero-uuid-recovery` (stop/verify/snapshot re-checked idempotently, `safe_to_bootstrap` on the candidate, bootstrap spec, start candidate, start the others one by one, steady-state spec, wait Synced, state check). | One operation: the positions can only be read on stopped nodes (the one-off `wsrep-recover` container refuses a mounted volume), but the approver should see the positions before the bootstrap is approved. |
| Phase 2 planning | `manager.ZeroUUIDReconciler` (leader-only) plans phase 2 after phase 1 succeeded: trusted evidence collection (the stored health predates the stop and is ignored), `galera.DiagnoseFullOutage`, `RecoveryPlan`. The link prepare -> recovery and the new operation commit in one transaction, so a leader change neither loses nor duplicates it. | In-memory callback: lost on failover. |
| Diagnosis | When every node holds the zero state (no real UUID anywhere) `DiagnoseFullOutage` returns `recovery_kind=zero-uuid-recovery`: candidate is the highest recovered local seqno; `auto_eligible` only if every position is readable and the top seqno unique. Mixed or diverging histories keep the ordinary diagnosis and are never auto-eligible. A zero-UUID Primary answers `409 zero_cluster_uuid_primary` with `offer: zero-uuid-recovery`. | Reporting `no_candidate`: left the operator without a path. |
| Ambiguity | Equal top seqno, unreadable or missing position, fewer than a majority readable: tie and unreadable are risks, `auto_eligible=false`, approval always needed; below a majority no candidate. | Lowest slot wins automatically on a tie: rejected, owner decision. |
| Snapshot | New agent command `snapshot-data` copies `data/` to `<volume>/snapshots/<name>/` on the same volume (modes, owners, times, links kept; complete only with a marker file; idempotent per name; an incomplete copy is redone). It refuses with `insufficient-space` (or when free space cannot be determined) and nothing is changed: the operator frees space or copies elsewhere, then starts again. | Docker volume copy or restic: more moving parts; a same-volume copy needs no network and no credentials. Costs one extra data-size of disk on each node volume. |
| Bootstrap | `mark-safe-to-bootstrap` gains `allow_zero_uuid`: only for a file that holds exactly the zero state; only the flag is set (no seqno written), so Galera creates a new state UUID. A real-history file is refused with it. | Writing the recovered seqno into a zero-UUID file: pointless, the history is lost. |
| Verification | New condition `state-recovered` (live probe): every node Synced, one Primary component of the expected size, one common non-zero state UUID. | Row-level data check: no allow-listed SQL template exists; not implemented (see limits). |
| Approval | The existing digest-bound flow. Operators propose (`operate`), administrators approve (`recover`, both phases), viewers read. Approvals by the policy are recorded with approver `policy:autoRecover` and the same digest binding. | A separate approval path: rejected. |
| autoRecover | Per-cluster opt-in (`PUT /clusters/{id}/auto-recover`, administrator, audited), default off. With it the leader starts phase 1 when a fresh zero-UUID Primary observation exists (cooldown of one hour after a run) and auto-approves phase 1 (stop and copy lose nothing); phase 2 is auto-approved only when `auto_eligible`; otherwise it waits for a human with the stopped nodes. | Auto-approving phase 1 is the one place the policy acts before positions are known: the stop of a cluster that already serves from a zero-UUID Primary and is reported unhealthy, with a snapshot first. If this is not wanted, leave autoRecover off. |
| Notifications | Before: `recovery.planned` (auto) or `recovery.needs_approval` (critical) for each phase; after: `recovery.ended` once per ended operation (info on success, critical otherwise), through the monitoring dispatcher; events are recorded either way. Reconciler-driven, so they survive failover. | |
| Never upgrades | The recovery plans never change the image (`Desired` specs carry the cluster image); an unfinished upgrade operation blocks a run (`busy`). | |

## Known limits

- Fakes only. The agent command was tested on a temporary directory, the planners and the two-phase flow on an in-process manager with a fake agent client; no real `wsrep-recover` container, SST or bootstrap ran. E12 verified the manual procedure, not this automation.
- The "data check" is the live state check (Synced, one Primary component, one new non-zero UUID on every node); table contents are not compared.
- The snapshot is a plain copy on the same volume: it does not protect against loss of that volume or host, and it is not a backup. It is never deleted automatically.
- Positions are the local InnoDB seqnos. If the highest node is not actually the most advanced (for example a node whose own `wsrep-recover` was skipped), transactions on the others are lost; the diagnosis shows unreadable positions as risks and never auto-eligible.
- The ordinary full-outage recovery gained the same mandatory snapshot steps and the state check.
- Not covered: stale single nodes (B3) are rebuilt by SST like all non-bootstrap nodes; a node whose SST fails leaves the operation failed with the cluster partially up.
