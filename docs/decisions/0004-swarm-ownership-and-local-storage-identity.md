# ADR 0004: Swarm service ownership and local-storage identity

Date: 2026-10-19
Status: Proposed; partly confirmed by lab experiments E1/E2 (arm64 only, one Swarm manager, three Lima VMs, Docker 29.9.1, MariaDB Galera). The design text below is unchanged except where the evidence section says otherwise.

## Context

Requirements: P04/P05 (manager deploys agents as services, one per host), A10 (do not modify unrelated resources), A02/A06 (automatic single-node replacement but never a bypass of quorum or guided full-cluster recovery), local storage without distributed volumes ([ARCHITEKTUR.md](../ARCHITEKTUR.md)). Swarm's scheduler may place a task on another host; an empty local volume there must never be mistaken for the old node.

## Proposed design

1. **Ownership labels and inventory.** Every managed Swarm object (service, network, config, secret, volume) carries labels `dbcm.installation`, `dbcm.cluster`, `dbcm.node` and is recorded with its Docker object ID in manager state. Labels are bookkeeping only, not a security boundary (see ARCHITEKTUR). The manager only modifies objects whose ID is in its inventory.
2. **One service per database node, pinned.** Each Galera node is its own Swarm service with replicas=1 and a placement constraint to one host (`node.id == <id>`). Swarm therefore restarts it on the same host but cannot silently move it. Moving or replacing a node is an explicit manager operation, never a scheduler side effect. This is how competing controllers are avoided: Swarm restarts containers, the manager decides identity and placement.
3. **Storage identity.** Each node has a durable `node-uuid` generated by the manager and stored in manager state and in a marker file on the node's local volume (together with installation and cluster IDs). The agent verifies marker and expected UUID before the database container may start; mismatch (missing marker on a non-empty target, or a foreign marker) blocks start and reports to the manager. An empty volume with no marker is only accepted when the manager has issued a "new identity" operation for that node.
4. **Replacement creates a new identity.** Replacement of a lost node allocates a new `node-uuid`, a new pinned service and a fresh volume, then syncs from a verified healthy donor. It runs only if quorum of the remaining nodes is intact and policy and capacity allow. Otherwise the cluster enters guided recovery (A06).
5. **Returning host.** A host that comes back with an old node's volume is reconciled by its marker: the old identity is either retired (service removed, volume kept for inspection until the user approves deletion) or explicitly rejoined; it never starts serving on its own.
6. **Agents.** One agent service per host (global mode, constrained to enrolled hosts). Agents execute only fenced commands ([ADR 0003](0003-manager-metadata-ha-and-fencing.md)) and refuse destructive operations without a current term.

## Alternatives

- One replicated service with N replicas and spread preferences: simple, but the scheduler decides placement and identity, which conflicts with the identity requirement.
- Distributed volume plugins: rejected by P07.
- Host-level systemd/container management outside Swarm: superseded by the Swarm-first decision.

## Open questions and required evidence (W05)

- Does Swarm honor `node.id` constraints plus `restart_policy` as assumed when a task fails, the host reboots, or the node is drained? What happens when the pinned node is `down` versus unreachable?
- Bind-mount versus named local volume for the data directory, and how the marker survives container recreation.
- Behavior when the Docker host is replaced but retains its node ID, or the Swarm node is removed and re-joined.
- Agent enrollment, identity and rotation (mTLS candidate) remain undesigned.
- Multi-Swarm isolation of installation IDs.

Evidence plan: dedicated lab VMs (W04), unrelated sentinel services before/after, host loss, host return with old volume, delayed messages and partition, as listed in [TESTING.md](../TESTING.md).

## Evidence (lab VMs, 2026-10-19)

Sources: [E1](../../tests/p0/results/e1-swarm-galera.md), [E2](../../tests/p0/results/e2-host-loss.md); scripts in `tests/p0/`. Each run created its own `dbcm-lab-` VMs through `bin/lab`, removed them afterwards, and left the unrelated Lima/Colima resources and a sentinel service unchanged.

| Assumption | Result |
| --- | --- |
| One service per node, replicas=1, pinned by `node.id` constraint, restarts on the same host | Confirmed: after `docker kill` the task restarted on the same node within 5 s |
| Pinned service is not rescheduled when its host is lost | Confirmed: after a forced VM stop the task stayed Pending ("no suitable node") and never moved |
| Returning host rejoins with its own volume | Confirmed: marker byte-identical, node rejoined (SST), row counts and checksums matched on all nodes |
| Swarm alone protects against an empty replacement volume | **Refuted**: the plain service started on an empty volume and joined the cluster after 18 s without any identity check. The marker guard (`tests/p0/marker-guard.sh`) refused the start; an explicit new-identity step then allowed it |
| Marker survives in the data directory | **Refuted**: SST deletes files in the datadir. The marker must live outside it, at the volume root |
| Minority partition cannot commit writes | Confirmed: the isolated node went non-Primary and refused reads and writes; the majority kept serving; no write from the isolated side was committed |

Further observations that affect the design:

- Failing or refused tasks restart roughly every 5-19 s with no backoff; the manager must detect and pause crash loops.
- Every return after an unclean stop used full SST, not IST; `--wsrep-recover` was not evaluated.
- `--wsrep-new-cluster` must be removed from the service spec after bootstrap or a restart could bootstrap a second cluster.
- Lima's default network gives no VM-to-VM path; the lab attaches the documented `lima:user-v2` network. A forced VM stop loses unsynced writes, so the agent must fsync identity markers.
- After a partition heals, Swarm replaced the old container; whether two containers briefly shared the datadir was not checked (`docker events` evidence is missing).

Not tested: graceful reboot and drain, loss of the manager host or of several managers, multiple Swarms, AMD64, the real agent (only shell scripts stood in for it), rootless Docker (the lab uses rootful Docker because the Lima `docker` template installs rootless).

## Evidence (lab VMs, E6, 2026-10-23)

Source: [E5/E6 results](../../tests/p0/results/e5-e6-proxy-outage.md). The real manager and mTLS agents on three arm64 Lima VMs; both outages were caused outside the manager.

| Assumption | Result |
| --- | --- |
| A full outage is diagnosed from the nodes' own evidence without starting anything | **Confirmed.** Clean (all services scaled to 0 at once): every grastate.dat had seqno 3338 and `safe_to_bootstrap: 0` (no "last node"); the diagnosis proposed n1 with a `tie` risk. Crash (SIGKILL of all three): seqno -1 everywhere; `GET` proposed no candidate and asked for `--wsrep-recover`. For 120 s no spec changed and no task ran. |
| `--wsrep-recover` gives the positions after a crash | **Confirmed** through the new agent command `wsrep-recover` (one-off container without network on the volume's host): seqno 3345 on all nodes, grastate.dat unchanged, no container left. mariadbd needs a cluster address even for `--wsrep-recover`; the agent passes an unreachable one, never `gcomm://`. |
| Guided recovery keeps node identities and data | **Confirmed** after one fix: the recovery restarted the existing services on their verified volumes, rows written before both outages were present. **Refuted at first:** bootstrapping the crash candidate from `seqno: -1` with only `safe_to_bootstrap: 1` started a new cluster state UUID; mark-safe now also writes the recovered seqno and the final run kept the UUID. |
| Swarm does not restart a service scaled to 0 | Confirmed: replacement tasks created by the restart policy after the SIGKILL stayed `Ready/Assigned` with desired state `Remove` and never ran. |

Open: joiners took a full SST in every recovery (also at equal seqno); a VM power loss with Docker and manager restarting; diverging histories and a missing node in the diagnosis on real nodes.
