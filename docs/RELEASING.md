# Release policy and operator checklist

The product name is **cluster-manager**; the repository and Go module retain `db-cluster-manager`. This policy governs manager, agent and CLI together. Database LTS/Rolling channels are separate. No release has been executed or verified yet.

## Version numbers

Use stable Semantic Versioning tags exactly `vMAJOR.MINOR.PATCH` (for example `v0.1.0`); no leading zeroes, prerelease suffixes or build metadata. Before 1.0, minor versions may change APIs or deployment contracts and patch versions should contain compatible fixes. After 1.0, increment major for incompatible public API or persisted-format changes, minor for compatible features, and patch for compatible fixes. The tag's version without `v` is injected into all three binaries and both images. Each release tag must point at a reviewed commit on the intended release line. Tags are immutable; fix a bad release with a new version.

Conventional commit subjects drive the changelog: `feat(scope): summary`, `fix(scope): summary`, `perf: summary`, `docs: summary`, and `type(scope)!: breaking summary`. Other subjects appear under Maintenance. The script selects the highest lower stable ancestor tag; the first release uses all history. It reads subjects only, so breaking changes described only in a commit body must also be summarized in a subject. [Release notes template](RELEASE_NOTES_TEMPLATE.md) supplies the fixed artifact and limits sections.

## CI publication boundary

`.github/workflows/release.yml` starts only on `v*` tag pushes and checks the exact tag format before publication. It reuses the read-only native build and race test workflow. After verification, it builds the UI once, then static Linux amd64 and arm64 manager, agent and CLI binaries with the version and commit embedded. Each archive contains all three binaries, `go version -m` reports and per-binary CycloneDX JSON SBOMs generated by the pinned `cyclonedx-gomod` Go tool with matching `GOOS`, `GOARCH` and `CGO_ENABLED`. The six SBOMs are also individual release assets. `SHA256SUMS` covers archives and standalone SBOMs.

The two published GHCR indexes are `ghcr.io/magicalwig34653/db-cluster-manager` and `ghcr.io/magicalwig34653/db-cluster-manager-jobs`, tagged with the full version and major.minor. Buildx emits SBOM and maximum-mode provenance attestations for each multi-platform image. The image job signs each pushed index **by digest** with keyless cosign and GitHub OIDC. Only that job has `packages: write` and `id-token: write`; only the final release job has `contents: write`. No repository or personal signing secret is configured. All Actions use SHAs already pinned in this repository; Go tools have explicit versions. The Python deployment checker guards these contracts but does not execute GitHub Actions, Docker or Sigstore.

Before an authorized tag push: review the staged diff for secrets and machine-local files, confirm all [R1/P0 gates](RELEASES.md) relevant to the release, run the local and native CI checks, inspect `scripts/release_notes.py` output, and review image base digests and bundled licenses. The owner must explicitly choose when to publish a release; this document creates no tag and changes no remote. After a tag-triggered run, verify the release assets and both image indexes/attestations/signatures before announcing availability. If any job fails, investigate and publish a new version; do not move an existing tag.

Consumers should download the matching archive and `SHA256SUMS`, run `sha256sum -c SHA256SUMS --ignore-missing`, then inspect the extracted SBOM and version. For an image, resolve the full immutable digest and use `cosign verify --certificate-identity-regexp 'https://github.com/MagicalWig34653/db-cluster-manager/.github/workflows/release.yml@refs/tags/v.*' --certificate-oidc-issuer https://token.actions.githubusercontent.com IMAGE@sha256:...`; inspect the certificate identity and digest. BuildKit provenance is attached to the image index, while the binary archives currently have checksums and SBOMs but **no independent signed provenance attestation**. This is a recorded limitation for a future package; checksums alone do not authenticate a download. The pipeline has not run, so the exact GHCR signing and verification behavior is unverified.

The release notes describe changes and artifacts, not production readiness. [Installation](INSTALL.md), [current status](STATUS.md), and [known limits](guides/en/10-known-limits.md) remain authoritative for trials.
